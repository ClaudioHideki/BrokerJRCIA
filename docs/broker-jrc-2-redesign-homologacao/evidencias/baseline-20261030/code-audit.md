## Segurança e integridade: o que o código sustenta

- Custódia: `0075_media_custody.sql:21-34` combina FKs compostas, FORCE RLS, SELECT/INSERT para app; trigger revalida autoridade e referências (`:38-75`). O ledger é imutável pela API/runtime. Exclusão administrativa/lifecycle preexistente continua distinta da política KEEP; a migration integra remoção dos recibos ao purge autorizado (`:77-86`). Portanto KEEP desta feature não equivale a promessa de que nenhum administrador pode apagar dados.
- Replay: funções SECURITY DEFINER com search_path fixo, revogação de PUBLIC e EXECUTE restrito (`0077:78-95,97-148,150-171`); lock da chave FOR UPDATE serializa intenção/autoridade; trava endpoint→event→delivery e revalida relógio após bloqueios. Trigger limita resets/estados e mantém lifetime_attempts (`:46-74`). Ledger acompanha prune30dias: não é auditoria definitiva independente.
- HTTP novo: scope específico, tenant extraído do principal, corpo estrito, problem-details sanitizado e no-store (`http/routes/media-custody.ts:10-36`; `http/routes/partner-webhooks.ts`). Testes negativos locais cobrem JWT/ADMIN insuficiente, scope, body/UUID e tenant injetado. Não houve pentest nem prova atual do catálogo/grants do servidor neste subtrabalho.
- Webhook parceiro: HMAC cobre timestamp/eventId/bytes exatos (`partner-events/worker.ts:13-16,63-67`); URL exige HTTPS e filtro SSRF (`:7-11`, `integrations/chatwoot-safe-http.ts`). Isso explica comportamentos possíveis, não a causa dos registros produtivos ainda sob investigação.
- Redis não é a outbox durável do Broker. Filas principais/leases são SQL; Redis serve controle/rate-limit/cache, incluindo cache engine. Compose prevê AOF/noeviction (`infra/dokploy/compose.yaml:523-530`), engine usa DB6 e persistência de mensagens/histórico (`:571-581`). `public-ingress-rate-limit.ts:53-54` retorna503 se controle falha. ## Falhas de mensagens versus falhas de delivery

`messaging_messages.state=FAILED` é distinto de `partner_event_deliveries.status=FAILED`. Mensagens têm retry seguro automático condicionado a `retry_safe`, ausência de lease e `<6` tentativas (`messaging/repository.ts:1118-1130`). Resultado incerto tem tratamento próprio, inclusive UNKNOWN e bloqueio/reconciliação, e não autoriza repetir como envio novo. Para QR, expiração é delegada ao recuperador específico (`:1138-1142`). B12 não altera esses caminhos.

`completeOutgoing` conserva outbox quando retry é comprovadamente seguro e a remove quando não é (`repository.ts:1563-1574`). Um FAILED sem outbox não prova perda: pode ser encerramento terminal intencional. Um UNKNOWN não prova não-envio. Causa dos números produtivos exige tabela/origem/provider/canal, classe canônica de erro, distribuição temporal, retry_safe, tentativas, lease e evidência técnica de upstream. Nenhum conteúdo/telefone/segredo precisa constar no relatório para essa triagem.
